- [ ] Optional login (anonymous device default)
  Identity decision recorded in the item above; this is the additive scope it implies. The default path — no sign-in, everything keyed on the existing device UUID — is already built and stays untouched; login must never be a prerequisite for any feature (guardrail: F2P parity).
  - [x] Decision (done): **all three mechanisms** — email/password, Google sign-in, and Apple sign-in, offered side by side in the sign-in UI. Carried consequences: email/password is the GDPR-heaviest surface (password reset + verification flows; guardrail 6 — plan the age rating with it in, and `TAG_FOR_CHILD_DIRECTED_TREATMENT` if that's the answer), and with a third-party (Google) login present, iOS "Sign in with Apple" is required — offered anyway, so the rule holds by construction.
  - [x] Server (`pb_hooks/`): DONE — provider-agnostic accounts (the three mechanisms create or sign into the SAME account; email where it exists is the shared identity; the merge rule is sub → email → create, pure in `logic.js`); the data endpoints (verify/restore/cloud/leaderboard) accept an optional `sessionToken` and key by account with the device id as fallback; sign-in BACKFILLS `accountId` onto the device's existing rows (set-only — data is never lost or duplicated); the GDPR `delete my data` endpoint gains the account target (account + all linked devices, entitlements included). Seven `auth/*` endpoints in `endpoints.js`/`handlerLib.js`, `accounts`/`authSessions` private collections in `collections.js`, sidecar `POST /identity` (Google RS256 via the well-known JWKS, Apple ES256 via `appleid.apple.com/auth/keys`, `aud`/`exp`/`iss` pinned) with the same fake-token sandbox / fail-closed modes as the store path. Contract + env in `pb_hooks/README.md`.
  - [ ] Client: settings sign-in/out with all three options visible ("continue without an account" is the visible default), claim/link flow for pre-existing device data, and the settings copy that is currently drafted for the device-only model (`delete my data`, reinstall caveats). The session token goes in secure storage (Keychain/Keystore — never AsyncStorage) and threads through `cloudSave.ts` / `iapProvider.ts` / `leaderboard.ts` as `sessionToken`. The two native SDKs (Google sign-in, Sign in with Apple; + secure storage for the email credentials) land in provider files behind the same pick-pattern as the store providers → `npx expo prebuild` after adding them.
